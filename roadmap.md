# Strix Roadmap

Forward-looking work for the Strix engine. Items below are prioritized by
user-visible impact: blockers for serious adoption first, then high-impact
additions, then nice-to-haves and research.

This roadmap is shaped by integration feedback — the bumps that show up when
real consumers (CI pipelines, headless wrappers, hosted platforms) drive
Strix at scale — and by the AI-security-engineer lens of "what does
comprehensive coverage actually require?". Most items are valuable to
direct CLI users; where an item is primarily a non-interactive concern,
the row says so.

Read alongside the [README](README.md) for what Strix already does and the
in-tree skills directory for how the agent's knowledge expands.

## 1. Scan readability — what was actually checked

A scan today emits agent identifiers, tool-call counts, and a final
`vulnerabilities/` directory. That tells the user *what was found* but not
*what was tried*. A clean run with zero findings is indistinguishable from a
broken run with zero findings. Closing that gap is the single biggest UX
improvement for non-CLI consumers (and a big one for the TUI).

| | Item | Why | Where | Effort |
|---|---|---|---|---|
| ✅ | **`run.test_plan` event after `run.configured`.** ([#35](https://github.com/ClatTribe/strix/pull/35)) | Lets any consumer (TUI, CI log, dashboard) answer "what is this scan doing?" before findings exist. | New `strix.telemetry.test_plan.build_test_plan(scan_config, dns_only)` derives the deterministic outer envelope of "things this run could find" from target type + flags, not the LLM's chain-of-thought (which doesn't exist at config time). Per-target-type category map covers domain (11 categories), web_application (14), ip_address (4), repository / local_code (5). Per-target entries carry `target_id`, `value`, `type`, `planned_categories` (with descriptions), and `skipped_categories` (with reason). dns_only mode prunes `subdomain_takeover` / `info_disclosure` / `mx_recon` from domain plans. Plain-English `summary_text` headline ("Plan: 1 domain target (example.com) with 11 planned check categories."). Emitted from `Tracer.set_scan_config` after `target.started` events; payload tolerates the same target shapes as the rest of the telemetry layer. | M |
| ✅ | **Phase-state events.** `phase.entered {phase}` for `recon`, `exploit`, `validate`, `report`. Tracer API: `enter_phase` / `complete_phase`. Agent-callable via the `record_phase` tool. ([#11](https://github.com/ClatTribe/strix/pull/11)) | Consumers can render a meaningful progress bar; the agent's own behaviour benefits from explicit phase boundaries (recon completeness check before exploit). | [`strix/agents/StrixAgent`](strix/agents/StrixAgent). | M |
| ✅ | **Semantic checkpoint events: `check.started` / `check.completed`.** Per attack class × surface. `result` ∈ {vulnerable, not_vulnerable, inconclusive} with confidence. Aggregated per-run via `get_check_summary` and persisted to `checks_summary.json`. The recon tools in §7.3 emit one check per sub-check automatically. ([#11](https://github.com/ClatTribe/strix/pull/11)) | A scan that tested 8 attack classes and found 2 vulns reads very differently from a scan that found 2 vulns with no idea what else was tried. This is the data behind a real coverage report and behind "negative coverage assertions" downstream. | New event types emitted from the per-class probe code. | M |
| ✅ | **Findings tagged with a semantic category enum**, not just CWE. Auto-inferred from CWE via a 32-CWE map; agent can override explicitly via the `category` parameter on `create_vulnerability_report`. ([#6](https://github.com/ClatTribe/strix/pull/6)) | CWE alone forces every consumer to redo keyword bucketing. Today downstream tools regex on title + CWE; that drifts. | `add_vulnerability_report` and the report dict shape in [`strix/tools/reporting`](strix/tools/reporting). | S |
| ✅ | **Per-agent `category` tag on `agent.created`.** ([#33](https://github.com/ClatTribe/strix/pull/33)) | Today downstream UIs render `agent.created.payload.task` verbatim, which is just the user's instruction echoed back. A category gives sub-agents named roles ("auth-attacker", "ssrf-scanner") rather than "Investigator #3". Pairs with §8's specialist-team architecture. | New `category` field on `AgentState` (default None). New `category` parameter on the `create_agent` tool — normalized lowercase + stripped. Plumbed through `BaseAgent` constructor → `tracer.log_agent_creation` → `agent.created` event payload + `tracer.agents[id]` dict + agents-graph node. Schema XML documents the parameter with example values (auth-attacker / sqli-validator / xss-specialist / ssrf-scanner) and updates the existing examples to demonstrate usage. | S |
| ✅ | **`run.summary` event at scan end.** ([#31](https://github.com/ClatTribe/strix/pull/31)) | Headline answer to "how did the scan go" in 10 seconds. Useful for CI exit logs, dashboard cards, Slack notifications. | New `Tracer.build_run_summary()` assembles a v1 payload: schema_version, run_id/name, duration_seconds, targets[], findings_summary{total, by_severity, by_category}, top_findings[≤5] sorted by severity, checks (full `get_check_summary()`), and a one-paragraph `summary_text`. Emitted via `run.summary` event right before `run.completed` so ordered consumers see the structured summary first. Persisted to `run_summary.json` alongside `events.jsonl` for filesystem consumers. | S |
| ✅ | **`target.started` / `target.completed` events** with the target value. ([#32](https://github.com/ClatTribe/strix/pull/32)) | Multi-target scans have no clean per-target progress today — consumers join across multiple events to figure out what's running where. | Auto-emitted from `Tracer.set_scan_config` (one `target.started` per entry, with stable `target_id` like `target-0001`) and `Tracer.save_run_data(mark_complete=True)` (one `target.completed` per started target, with per-target rollup of findings.by_severity / findings.by_category / checks.total / checks.by_category). New `Tracer.build_target_rollup(value)` does the per-target slice; new module-level `_normalize_target_for_events` accepts string / `{value,type}` / CLI's `{type,details,original}` shapes. Order: `target.started` after `run.configured`, `target.completed` before `run.summary`. Idempotent on the completion side. | S |
| ✅ | **`finding.kill_chain` event for multi-step findings.** ([#36](https://github.com/ClatTribe/strix/pull/36)) | "Pattern matcher" tools emit findings as standalone alerts. A real adversarial agent's value is the chain. | Event populated when a finding is finalized *with* a chain (silence is honest for single-step pattern matches). New `kill_chain` parameter on `Tracer.add_vulnerability_report` and `create_vulnerability_report` tool. Agent-facing input is XML (`<step number="N" type="...">…</step>`); types clamp to a 7-value set (`recon` / `discovery` / `exploitation` / `escalation` / `lateral_movement` / `impact` / `validation`). Each step normalizes to `{step_number, type, description?, tool?, evidence?, agent_id?}`; empty-content steps dropped. Event payload links to the finding via `report_id` + `fingerprint`, includes `step_count` for fast UI rendering. Persisted on the report dict so `vulnerabilities.json` carries it. Order: `finding.created` then `finding.kill_chain`. | M |

## 2. Authenticated web application testing

The single biggest coverage gap in Strix today: most real apps live behind a
login, and the only way to authenticate the agent is to put credentials in
`--instruction` text. That works inconsistently, and the credentials end up
in `events.jsonl` and the LLM's conversation history. Every team running
Strix against a non-trivial web app hits this.

| | Item | Why | Where | Effort |
|---|---|---|---|---|
| ✅ | **`--auth-cookie <value>`, `--auth-bearer <token>`, `--auth-basic <user:pass>` flags.** ([#40](https://github.com/ClatTribe/strix/pull/40)) | The fragile-by-default behavior today is the docs-prescribed pattern. A first-class flag means credentials cross the host→sandbox boundary as a transport concern, not a prompt concern. | Values cross host→sandbox via `STRIX_AUTH_*` env vars (forwarded by `docker_runtime.py`); never written to `events.jsonl`, the agent prompt, or tool outputs. New `strix/tools/proxy/http_safety.py` module — `inject_auth_headers()` reads env at request time and merges into outgoing headers. Agent-supplied headers WIN on conflict (lets the agent test specific auth scenarios without the global override fighting back). Bearer wins over basic when both set. Agent gets a content-free instruction-block ("credentials configured; you can't see the values; treat the app as authenticated"). | M |
| ✅ | **`--header <name:value>` (repeatable).** ([#40](https://github.com/ClatTribe/strix/pull/40)) | Any non-cookie/bearer auth scheme today has to live in the instruction. Breaks for any header-driven gateway. | JSON-encoded list forwarded via `STRIX_HEADERS` env. First-colon split preserves values that themselves contain colons. Agent-set values not clobbered. Header *names* surface in the instruction block (auditable); values stay in env. | S |
| ⬜ | **Recorded-login replay for SSO / MFA.** A user records a login flow once (Playwright codegen-style); Strix replays it at scan start to acquire session state. WebAuthn / passkeys / hardware keys remain out of reach by design. | Today TOTP can be hand-fed via instruction; SSO redirects often work but with no guarantee; passkeys are impossible. Recorded replay is the standard escape hatch in commercial scanners. | New tool/recording mode + sandbox-side replay using existing Playwright integration. | L |
| ⬜ | **Built-in read-only IAM-style scan profile pattern**, documented. Once the auth flags above land, ship a documented pattern: provision a least-privilege test account, point Strix at it, rotate after the run. | Hygiene guidance shipped *with* Strix, not as a thing every user invents. | New section in [README](README.md) + a skill in `strix/skills/`. | S |

## 3. Per-target-type CLI flags

Strix's CLI today is intentionally small — `-t`, `-m`, `--instruction`,
`--scope-mode`, `--diff-base`. Per-target-type options end up in the
free-text `--instruction`, which the model honours about 80% of the time.
That's fine for hints (language, branch); it's not fine for safety-critical
controls (rate limits, exclude paths) where compliance matters.

Each item below is a thin flag with a clear semantic — a wrapper around an
existing tool the agent already invokes (`git clone`, `nmap`, the HTTP tool).

| | Item | Target type | Why | Proposed shape | Effort |
|---|---|---|---|---|---|
| ⬜ | **`--branch <ref>`** | `repository` | Today Strix clones the default branch. Security-conscious teams want to scan `develop` or `staging`. | Single string; passed to `git clone --branch` in [`clone_repository`](strix/interface/utils.py). Strix logs the resolved ref. | S |
| ✅ | **`--seed-url <url>` (repeatable)** ([#41](https://github.com/ClatTribe/strix/pull/41)) | `web_application` | Steer the crawl. "Don't start at /, start at /api and /admin." Pairs with the recon-first pipeline (§7) — a pre-scan crawl can hand seeds in. | Forwarded via `STRIX_SEED_URLS` env (comma-separated). The new `bfs_crawl` tool reads it automatically; off-scope seeds are dropped before crawl starts. Agent gets an instruction-block listing the seeds. | S |
| ✅ | **`--exclude-path <glob>` (repeatable)** ([#40](https://github.com/ClatTribe/strix/pull/40)) | `web_application` | "Don't hit `/api/billing/charge` or `/admin/destroy-account`." Hard rule, not a hint. | Forwarded via `STRIX_EXCLUDE_PATHS` env (JSON list). `is_path_excluded()` short-circuits in `proxy_manager.send_simple_request` BEFORE network dispatch. fnmatch glob syntax; path-only matching (query string discarded so `?path=...` can't dodge). Excluded request returns a structured `{skipped: True, reason: "excluded", matched_glob}` response — the agent gets a clear signal to route around. Doesn't consume rate-limit budget. Agent instruction block lists the excluded paths verbatim. | M |
| ✅ | **`--openapi <url>`** ([#41](https://github.com/ClatTribe/strix/pull/41)) | `web_application` | Test every documented endpoint. Today the agent has to discover the spec via crawl. | Forwarded via `STRIX_OPENAPI_URL`. `bfs_crawl` fetches the spec, supports OpenAPI 2.x (host + basePath) + 3.x (servers[0].url), parses paths/methods, seeds GET endpoints into the crawl, records every method as an endpoint with `discovered_via=openapi`. JSON only (YAML not supported in the sandbox). Failures recorded in the crawl's `errors[]` rather than crashing. | S |
| ✅ | **`--rate-limit <qps>`** ([#40](https://github.com/ClatTribe/strix/pull/40)) | `web_application` | "Don't exceed 10 req/s — production traffic." | Forwarded via `STRIX_RATE_LIMIT` env. `throttle_for_rate_limit()` is a single global token bucket inside the sandbox process — sleeps to maintain the configured min-interval between dispatched requests. Cap is across the whole sandbox process (not per-host) — trades simplicity for predictability. Excluded requests (above) skip throttling so paced testing doesn't get penalized for excluded paths. Agent instruction block surfaces the configured cap. | M |
| ✅ | **`--dns-only`** ([#30](https://github.com/ClatTribe/strix/pull/30)) | `domain` | Surface mapping without active probing. | New CLI flag. Sets `STRIX_DNS_ONLY=1` (forwarded into the sandbox via `docker_runtime`) which `domain_recon_pipeline` reads to force `dns_only=True`. In dns_only mode the orchestrator skips: subdomain triage HEAD probes, subdomain-takeover fingerprint fetches, cloud-asset HEAD probes. Pure DNS + third-party APIs (dns_hygiene, org_fingerprint, passive_dns_history, subdomain_enum's passive sources, reverse_ip_discovery, code_search_for_domain, saas_leak_discovery) all run normally. The `surface_map.json` artifact carries `dns_only: true` so consumers can see the mode the scan ran in. CLI also injects an instruction block telling the agent. | S |
| ⬜ | **`--ports <spec>`** + **`--protocol <tcp\|udp\|both>`** | `ip_address` | Today's port/protocol selection lives inside the agent's nmap invocation. SMB / IoT users want explicit control. | Passed straight through to the underlying nmap command. | S |
| ⬜ | **CIDR / IP-range support on `-t`** | `ip_address` | "Scan my office's `203.0.113.0/24`." Today only single IPs are accepted. | Validator update + per-host fan-out (or pass-through if nmap can take it directly). | S |
| ✅ | **`--preflight` / fail-fast unreachable check** ([#29](https://github.com/ClatTribe/strix/pull/29)) | all network targets | A scan that runs for 10 minutes and finds nothing because the target was down is the worst-feeling failure mode. Resolve DNS + single HEAD/TCP probe before spawning the agent loop. New `strix.interface.preflight` module: per-target DNS resolve + TCP probe (web: 443→80; ip: 443/80/22/25). Default-enabled via `argparse.BooleanOptionalAction`; `--no-preflight` disables. All-unreachable → exit 1 with rich diagnostic; partial-unreachable → warn + prune the dead targets and continue. Per-target budget ~7s worst case. | New phase before the recon phase in §7. | S |

Until each of these lands, the documented pattern stays "put it in
`--instruction`". When a flag lands, the corresponding instruction-augmentation
pattern in consumer wrappers can be deleted.

## 4. Cost, control, and resilience

A long Strix run is expensive. Today, runaway protection is the user's
responsibility — set `--max-iterations`, watch the rendered stats panel,
hope. These items move that responsibility into the engine.

| | Item | Why | Where | Effort |
|---|---|---|---|---|
| ✅ | **`--max-cost <usd>` and `--max-input-tokens <n>` flags with self-exit.** ([#113](https://github.com/ClatTribe/strix/pull/113)) Strix exits cleanly with a documented exit code (`3` = budget exceeded) and emits a `run.terminated` event. | Belt-and-braces against runaway. The cost panel shows totals only after they've been spent; a budget cap stops the spend. | New `strix/llm/run_budget.py` module — process-wide thread-safe accumulator that aggregates token / cost usage across every `LLM` instance in a run (vs. per-sub-agent budgets in #88, which cap a single specialist). Reads `STRIX_MAX_COST_USD` / `STRIX_MAX_INPUT_TOKENS_RUN` env vars (set by the new CLI flags); both default to 0 = unlimited. `record_run_usage` called from `LLM._update_usage_stats` after every round-trip. `is_run_budget_exceeded` returns `(bool, dimension)` and is **latched** — once tripped, stays tripped even if env vars change mid-flight (prevents a wrapper from accidentally clearing the cap). On first breach, `emit_run_terminated_event_once` fires `run.terminated` with full payload (`{reason: "budget_exceeded", budget_dimension, limits, consumed}`). The agent loop in `BaseAgent.agent_loop` polls `is_run_budget_exceeded` every iteration and calls `state.request_stop()` so every running agent terminates cleanly. The runner in `interface/main.py` reads the latch at scan-end and exits with `EXIT_BUDGET_EXCEEDED (3)` instead of `0`/`2`. Findings emitted up to the termination point are still in `vulnerabilities.json` — the run is partial. New CLI flags `--max-cost <USD>` / `--max-input-tokens <N>` in the production-safety arg group; both validated for positivity (negative or zero → exit 2 with diagnostic). 16 hermetic tests covering: accumulation across calls, ignore-zero-or-negative, no-cap-never-exceeded, cap-below/at/over-threshold, zero-means-unlimited, latch-sticks-even-if-env-changes, run.terminated emitted exactly once, no-event-when-not-exceeded, thread-safety (200 threads × 100 increments → correct total), env-var parsing (with garbage handling). 536 sweep across tests/llm/ + tests/agents/ + tests/telemetry/ — green. | LLM call site in [`strix/llm/llm.py`](strix/llm/llm.py); exit-code handling in [`strix/interface/main.py`](strix/interface/main.py); new module [`strix/llm/run_budget.py`](strix/llm/run_budget.py); agent-loop hook in [`strix/agents/base_agent.py`](strix/agents/base_agent.py). | M |
| ✅ | **Retry transient LLM 5xx / rate-limits with exponential backoff.** ([#112](https://github.com/ClatTribe/strix/pull/112)) Real incident: a Gemini `503 ServiceUnavailableError` mid-scan exits Strix immediately, throwing away a 7-minute agent context. Retry 2–3 times with `5s / 15s / 45s` backoff on 429/502/503/504 and `litellm.ServiceUnavailableError`. Emit `llm.retry_attempted` events. Only exit 1 if all retries fail. | A 30-minute scan disappearing because of one transient upstream blip is the worst-feeling failure mode. | The retry loop in [`strix/llm/llm.py`](strix/llm/llm.py) `LLM.generate` already retried (the wrapper code was `2 * (2**attempt)` with no event emission). PR #112 changes the schedule to the documented `5 * 3**attempt` (5s / 15s / 45s) capped at 90s, adds ±20% jitter so concurrent strix runs don't lock-step into the upstream's rate-limiter, and emits a structured `llm.retry_attempted` event per retry with `{attempt, max_retries, wait_seconds, status_code, error_type, error_message}` plus an `actor` block carrying `agent_id` / `agent_name` / `model`. Best-effort emission — tracer failures never break the retry loop. Status-code retry decisions delegated to `litellm._should_retry` (covers 429/502/503/504/timeouts). 12 hermetic tests covering: retry-on-429/502/503/504, no-retry-on-400/401, 5/15/45 schedule with bounds-checked jitter, 90s cap on long backoffs, retry-event-emitted-per-retry with full schema, agent+model on event, no-event-on-first-try-success, broken-tracer-doesn't-break-retry. 346 sweep across tests/llm/ + tests/telemetry/ — green. | S |
| ✅ | **Clean SIGTERM handling.** ([#114](https://github.com/ClatTribe/strix/pull/114)) On SIGTERM: cancel in-flight LLM call, flush `events.jsonl`, emit `run.cancelled`, tear down the sandbox, exit 143. Document the contract. | A scan-cancel button in any wrapper needs a signal it can trust. ## 7. Comprehensive coverage and recon pipeline

Sections 1–6 are about the contract between Strix and its consumers. This
section is about the **scan itself**: what does an AI security engineer
actually need Strix to do to claim "comprehensive coverage" of a target?

Today the agent decides what to do organically. That works — it's the
whole point — but it makes coverage probabilistic. A model that's tired,
distracted, or context-pressured may skip a category. The items below
introduce structured guarantees on top of agent improvisation: explicit
phases, tech-driven skill loading, and a coverage matrix the agent has to
clear before it can claim the scan is done.

The section is organized by target type because that's the natural way an
AI security engineer thinks about coverage — code targets need taint and
reachability analysis, web apps need an authz matrix and GraphQL handling,
domains need DNS hygiene and takeover detection, IPs need service-specialist
depth. The §7.0 foundations apply to every target type; the per-type
subsections list the specialist gaps.

## 8. Specialist sub-agent teams per target type

Sections 1–7 are individual capability gaps. This section is the
**architectural commitment** that makes them sustainable.

Today Strix has multi-agent capability — the lead `StrixAgent` can
spawn sub-agents via `agents_graph` — but no structural commitment to
per-target specialization. The lead improvises which sub-agents to
spawn and what to delegate. The result is closer to *one strong
generalist with a bag of tools* than to a structured pen-test team. As
target complexity grows, the generalist's coverage starts to depend on
context size and model attention — both of which are noisy.

The shift is to **specialist sub-agent teams per target type**. Each
team has a lead (planner), a recon group, an exploit group, a validate
group, and a reporter. Each specialist owns one job, runs to a tight
budget, and emits canonical findings.

Three commitments make this tractable:

1. **Phase gating.** Recon must complete (and emit `surface_map`)
   before exploit starts. Exploit emits `candidate_findings`; validate
   consumes them; report consumes verified findings only. No phase
   blurring. Connects to §1 phase-state events and §7.0 explicit recon
   phase.

2. **Specialist scope.** Each sub-agent has one job, a tight system
   prompt, ~20 iterations max, and emits canonical findings. The model
   spends compute on the work, not on context-juggling. Concretely:
   the SQLi specialist's system prompt does not include the SSRF
   skill — and vice versa.

3. **Structured handoffs.** Recon → exploit handoff is `surface_map`.
   Exploit → validate is `candidate_findings`. Validate → report is
   `verified_findings` with PoCs. No prose-as-state — every handoff is
   a typed JSON artifact written to the run directory.

The sections below define the team roster per target type. Building the
teams is incremental: ship the lead-team scaffolding first (§8.0), then
one specialist per team per release.

## 12. Triage and continuous-learning hooks

## 15. Research and longer-horizon ideas

Lower-confidence items. Listed for tracking, not committed.

- **Plan-then-execute mode.** Emit `run.test_plan` (§1) for review *before* spending tokens. Useful for high-cost scans where a human should approve scope.
- **Replay scan from a specific commit.** Re-run a prior scan against a different commit to verify a fix landed. Needs deterministic-enough sandboxing to be meaningful.
- **Differential triage signal.** When a finding's confidence shifts between scans (codebase changed, model changed), surface the delta and the reasoning rather than emitting a fresh finding.
- **Auto-remediation safety nets.** Before applying a generated patch, verify existing tests pass *and* add a regression test that the original PoC no longer exploits. Pairs with the triage hooks in §12.
- **Anonymized cross-org benchmarks.** Voluntary opt-in: "your stack typically has 3 SSRFs; you have 1." Privacy-respecting; the data is aggregated across consenting users only.
- **Threat-model-driven scanning.** Let users describe their app's architecture once (data-flow diagram, trust boundaries); the agent uses it as scaffolding. Pairs with §10's threat-intel feeds for enterprise relevance and with §14's structured threat-model input.
- **Bug-bounty disclosure pattern feed.** Anonymous learning from public HackerOne / Bugcrowd disclosures — extract the attack pattern, normalize it as a skill, ship the skill. The hard part is the legal/ethical review.
- **Specialist-team cross-pollination.** A finding by the Web-app team's IDOR specialist sometimes hints at a related Code team Authz check (e.g., "this endpoint missed `@require_role` decorator"). Today the teams are siloed; cross-pollination would let one team's finding spawn a targeted check in another.

## How to land an item

1. Open an issue referencing the row above.
2. For event-shape changes (§1, §5, §12): include the proposed JSON shape in the issue. Once shipped, document the event in the [README](README.md).
3. For new flags (§2, §3, §4, §11, §14): note the proposed semantic and how it interacts with existing flags. Flags that overlap with `--instruction` should clearly document precedence.
4. For new tools or skills (§7, §9, §10): the contribution should include a documented capability matrix (target types it applies to, categories it covers, expected runtime).
5. For new sub-agent specialists (§8): include the system prompt, the iteration/token budget, the input/output schemas, and at least one end-to-end integration test against a known-vulnerable fixture.
6. When an item ships, strike through the row and link the merged PR.

This roadmap is a living document. Items move between sections as we learn,
and "P0" today is whatever blocks real users from real outcomes — not a
fixed promise.
