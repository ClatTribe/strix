## Remaining iters (specified, not yet implemented)

### Q5.7 — `query_threat_intel(cve|cwe|product|domain, ...)`

**Status:** spec ready, ~400 LOC + 20 tests, no code shipped.

**What it does:** Unified real-time fetcher that collapses 4 existing wrappers (`cve_lookup`, `nvd_lookup`, `cve_intel_search`, `kev_diff_check`) behind one signature. Returns CVSS + KEV listing + EPSS score + vendor advisories + exploit availability. 24h cache.

**Why it's load-bearing:** Per CLAUDE.md §1.5.6, the FETCH EXTERNAL bucket is currently empty — the lead writes CVE/threat metadata from training-data memory, months stale. This tool gives the lead current data per scan.

**Acceptance:** added to `_MINIMAL_CORE_TOOLS`; every CV-report carries `query_threat_intel`-sourced KEV/EPSS metadata when a CVE is attached.

### Q5.7a — extend `query_threat_intel(domain=...)`

**Status:** depends on Q5.7. ~150 LOC + 10 tests.

**What it does:** Adds a `domain=` route to query_threat_intel that returns passive DNS / WHOIS / domain reputation. Closes the domain-asset intel gap.

### Q5.8 — `lookup_compliance_mapping(finding_shape, frameworks)`

**Status:** spec ready, ~250 LOC + 15 tests + cron corpus refresher.

**What it does:** Maps a finding shape (CWE + severity) to current SOC2/PCI/HIPAA control IDs. Backed by a versioned corpus refreshed on cron.

**Why it's load-bearing:** Currently the lead writes compliance mapping from memory — wrong year / wrong version. This tool gives current mappings deterministically.

### Q5.9 — `rescan(tool_name, target, captured_state)`

**Status:** spec ready, ~200 LOC + 15 tests.

**What it does:** Re-dispatches an L1 OSS tool from `anchor_prepass` with new state. E.g., after `scan_auth_flow` captures a session, the lead calls `rescan("scan_sqli_sqlmap", url, {auth_cookie: ...})` to re-test SQLi as the authed user.

**Safety:** `tool_name` validated against an allow-list (same OSS-wrappers in `anchor_prepass`). Capped at 5 rescans/scan (iter-29.9 destructive-amplification guard pattern).

### Q5.11a — `create_vulnerability_report` 21→7 parameter split

**Status:** spec ready, ~150 LOC + 15 tests.

**What it does:** Splits the current 21-parameter surface into:
- **Required-to-commit (7 fields):** title, target, evidence, severity, cwe, technical_analysis, poc
- **Render-on-finish (14 fields):** description_plain, business_impact_plain, recommended_action, fix_time_estimate, etc. — auto-generated at `finish_scan` time from finding context

**Why it matters:** Empirically (per `bench_context.py`) the lead leaves the plain-English fields empty most calls. Auto-rendering them at scan-end from the structured fact-base lifts L2-audience artifact quality.

### Q5.13 — customer-context per-scan config

**Status:** spec ready, ~80 LOC + 10 tests + docs.

**What it does:** Adds `customer_context = {industry, compliance_targets, critical_assets, threat_model}` to `system_prompt_context`. Rendered into the system prompt each turn (same path as SecurityContext re-render in `llm.py:496`).

**Why:** Without this, `customer_priority` (Q5.11 parameter) is a guess. The lead has no signal of what kind of customer this is.

### Q5.14 — `get_recon_artifact(kind, name=None)`

**Status:** spec ready, ~150 LOC + 10 tests.

**What it does:** Reads a specific recon artifact (`endpoints`, `openapi_spec`, `graphql_schema`, `sbom`, `subdomains`, `tech_stack`, `auth_endpoints`) persisted by anchor_prepass to `<run_dir>/recon/`.

**Why:** Prepass produces katana crawl output, OpenAPI specs, GraphQL schemas, SBOMs. These aren't findings — they're raw recon data the lead may want to grep or re-read. Currently lost to compaction.

**Cap pressure:** Adding to CORE pushes some assets to 11. Two resolution paths:
- (a) Collapse all READ STATE under `read_state(kind, ...)` umbrella (preferred)
- (b) Accept 11 as the new cap empirically — Q5.20 measures degradation
